# Un-install ledger

Keep a reversible, install-specific Markdown record under `~/.local/uninstall/`. An uninstall request starts by finding the matching record there (or the project's `UNINSTALL.md`), checking it against the current system, and using it to remove only what belongs to that installation. Existing records are evidence, not blindly executable scripts.

## Install or update

1. Identify the owning project (if any), install mechanism, target paths, and pre-existing state **before** changing anything. Include all affected layers: OS packages, package-manager entries, language dependencies, lockfiles/manifests, global executables, source trees, generated files, services, config, PATH/shell changes, caches/data, and external repositories/keys. For a language with its own dependency manager, inspect its actual manifest/lockfile and manager commands rather than treating `make install` or an OS package as the entire install. This includes e.g. npm/pnpm/yarn/bun, pip/uv/Poetry/Conda, Cargo, Go modules, RubyGems/Bundler, Composer, Maven/Gradle, NuGet, SwiftPM, pub, Mix/Hex, Julia Pkg, R/renv, and any other manager used by the project. Distinguish direct additions from pre-existing or shared dependencies; record exact versions/locations where useful.
2. Perform the installation. Capture the actual commands and *relevant, sanitized* output (`make install` file lists, package manager transaction summaries, etc.) and compare before/after state. Record what actually changed, including partial failures and side effects; a guessed inverse command is not an inventory. Never copy secrets or sensitive logs into the ledger.
3. Write or update one Markdown file per installation in `~/.local/uninstall/` (use a descriptive, collision-resistant name, e.g. `<project>-<component>-<date>.md`). It must stand alone: identify the install, date, project path if any, exact installed artifacts/dependencies and their owners, what existed before, the commands/output or paths that establish the inventory, ordered removal or restore steps, shared-resource cautions, and concrete post-removal checks. For language dependencies explain how to reverse additions in the **same** manager and restore manifest/lockfile changes; separate project deps from global packages, environments and caches. Include exact uninstall commands for OS packages only when known, with a review of the package manager's proposed removals before confirmation. If an inverse is uncertain, give an inspection step and state what remains unknown instead of inventing one. Preserve user data and shared dependencies by default.
4. If there is a writable project root, link its `UNINSTALL.md` to the ledger file (relative symlink where practicable). If it exists already, inspect and preserve it: update the matching existing ledger, or add a discoverable pointer for multiple installs rather than overwriting unrelated content. Append a short, non-duplicate line to the project's `AGENTS.md` pointing agents to `UNINSTALL.md` for installation/uninstallation instructions; create `AGENTS.md` only if appropriate for that project. If either change is unsafe or not possible, keep the central ledger and report why it was not linked. Avoid placing private machine details into a public project file; verify symlink and ignore/tracking policy before adding it to a repository.
5. Verify the ledger describes the observed changes and the project pointer resolves to it. Report the ledger path and any residual or unrecorded changes.

## Uninstall

1. Read the relevant ledger and verify the target, installed versions, ownership, and current paths against the live system. For older installs without a record, reconstruct a ledger from available evidence first and mark uncertainties. Check all language-specific dependencies and manifest/lockfile edits as well as system packages and installed files.
2. Follow the recorded steps in dependency-safe order. Inspect package-manager removal plans before accepting them. Remove only installation-owned artifacts; use the PATH-resolved `rm` for deletions where `rm` is needed (the local wrapper moves files to Trash). Preserve pre-existing/shared resources and user data, and ask before destructive or ambiguous removals.
3. Verify absence or restoration using the ledger's checks. Update the central Markdown record with the date, outcome, remaining items and blockers; keep the record for audit. If the project pointer or `AGENTS.md` line is now obsolete, remove only this installation's pointer/line when safe, leaving other installation records discoverable. Report what remains.
